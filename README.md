# 吃什么 · 回家做饭的菜单协作工具

打开冰箱，把现有的东西填进去，挑出今晚做哪几道；然后把菜单给要一起吃饭的人，
他们点完、给想吃的程度打个星，你这边就收到。

**解决的是分工问题**：谁做、谁吃、吃什么，这三件事在群里来回问十几条消息也定不下来。

纯静态前端，**零依赖、零构建**，不需要 `npm install`，不需要打包工具。
仓库根目录直接丢给任意静态托管就能跑。

## 两种角色

一个站，两个入口，对着的是两种完全不同的人：

**下厨的人** —— 填家里现有的食材 → 挑菜 → 生成菜单二维码 → 发出去。
别人点单回传后，工作台顶部出现未读角标。

> **站里不调任何大模型。** 挑菜的提示词由页面按你填的食材和条件拼好、给你复制，
> 你拿到自己手机上的 AI 应用里跑一遍，再把结果粘回来 —— 算力是你自己的，
> 站点这边零成本、零密钥、也不会偷偷花掉搭建者的额度。

**点菜的人** —— 扫那个码（或点开链接）→ 挑想吃的 → 给每道菜打星 →
提交，或者留句话。菜单上没有的可以自己加。

没有注册、没有登录、没有账号，也没有密钥。菜单本身就在他手上那个网址里。

## 两条通道

这是这个站最核心的设计。**点单从点菜的人手上回到下厨的人手上，有两条路**，
能走第二条就走第二条，走不通就安静地退回第一条 —— 而且是在用户完全无感的情况下。

### ① 离线通道：数据跟着链接走（永远可用）

菜单和点单都被压进网址的 `#` 后面，编解码全在浏览器里。
`#` 之后的部分浏览器不会发给服务器，所以**这条路上没有任何服务器参与**。

- 载荷 = `~` + 一位编码方式（`0` 原样 / `1` deflate 压缩）+ base64url 正文
- 前缀用 `~` 是因为它不在 base64url 的字符集里，放进网址不用转义、过微信也不会被吃掉，
  而且天然不可能和正文撞车
- 压缩走浏览器原生的 `CompressionStream('deflate-raw')`（Chrome 103+ / Safari 16.4+ /
  Firefox 113+）。老浏览器没有它也能用，只是链接长一些 —— 不压缩不是错误
- 一份 8 道菜的完整菜单：JSON 6,285 字符 → 打包后 **1,365 字符** → 二维码**版本 27**
- 一份点单：**409 字符** → 二维码**版本 20**

二维码密度有上限（超过 137 模块就不给了）：模块一多，手机屏上就得怼得很近才扫得出。
装不下就退一步去掉做法和教程；再装不下就只给链接，**宁可不给，也不给一个扫不动的码**。

这条路的代价是：点完菜，得把那段内容复制出来、用微信发给下厨的人，他再粘一次。
不好用，但它永远在。

### ② 在线通道：自带的小后端（可选）

在站点根目录放一个 `_worker.js`，家人的点单一提交就直接落到那儿，
下厨的人那边自动就收到了。

前端每次进页面先问一次 `/api/ping`：

- 回答 `kv: true` → 走在线通道，家人的点单自己进来。**页面上不做任何标记** ——
  已经自动收到的东西旁边再写一句说明，只会让人怀疑是不是没送到
- 回答 `kv: false`、404、断网、返回的不是 JSON → **整个会话都不再问**，
  界面退回"粘贴为主"的老样子

所有失败都是**安静地失败**：返回 `false` / `null`，不弹提示、不报错、不白屏。
用户甚至不知道少了一条路。

要用它见下面的「后端」。

### ③ 装成 App：安卓安装包（可选）

整个站点也能打成一个 APK，推到 `main` 后由 GitHub Actions 自动出包，挂在
Release `apk-latest` 上：

```
https://github.com/zhouxuan078-max/what-to-cook/releases/latest/download/WhatToCook.apk
```

装上以后桌面直接有图标、不经过浏览器，菜单和点单记录也不会被「清除浏览器缓存」
带走。工程在 `android-app/`，细节见那里的 `README.md`。

★ **壳里 ② 换了一条腿走路，这是这个 App 最要紧的一处。**

页面在壳里跑在假域名 `appassets.androidplatform.net` 上，站里写的**相对地址**
`/api/...` 会指到壳自己身上（那边没有后端，必然 404）；而让页面的 `fetch`
直接连真后端也不行 —— 真后端**故意**不返回任何 CORS 头（见「安全边界」），
跨域会被浏览器拦下。

所以壳里改由**原生代码**去发这条 HTTP 请求：原生发请求不涉及同源策略，
CORS 这回事根本不存在，后端也就不必为了 App 去开那个口子。
页面那一侧在 `assets/net.js`（`reqViaShell` + `window.KF_HTTP.done`），
原生那一侧在 `android-app/.../MainActivity.java`（`httpRequest`），
两边靠一个编号 `id` 对号入座。

网页那边一个字节都没变：判据是 `AndroidShell.httpRequest` 这个方法存不存在，
浏览器里没有它，`req` 照旧走 `fetch`。

> 🔴 后端地址在**两处**写着，改一个就得改另一个：
> `assets/net.js` 的 `API_BASE` 和 `MainActivity.java` 的 `API_ORIGIN`。
> CI 里有一道检查会把它们对一下。

## 本地跑起来

没有构建步骤。任选一种：

```bash
# 方式一：起个静态服务（推荐）
python -m http.server 8080

# 方式二：直接双击 index.html
# 也能跑，但「添加到主屏幕」这类需要 http(s) 协议的能力会失效
```

打开 `http://localhost:8080`。

没有任何东西要配置。**不改任何文件就能完整使用** —— 本地打开时没有后端，
站会自己认出这一点，走离线通道，功能一个不少。

## 后端（可选）

只有一件事需要服务端：让家人的点单自动回到你手上。
不做这件事，站照样完整可用，只是多点两下复制粘贴。

要让自动收单生效，在 Cloudflare 上做两步（一次性，约五分钟）：

1. **建一个 KV 命名空间**（存储和数据库 → KV → 创建）
2. **在 Pages 项目里加一条绑定**（设置 → 绑定 → KV 命名空间）
   - 变量名称必须一字不差是 **`KF_KV`**
   - 命名空间选刚建的那个

然后重新部署一次。验证方法：打开 `https://<你的域名>/api/ping`，
看到 `{"ok":true,"service":"what-to-cook","kv":true}` 就成了。

### 接口

只有三个，全部限定在 `/api/*`（见 `_routes.json`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/ping` | 后端在不在、KV 绑没绑。前端靠它决定走哪条通道 |
| `POST` | `/api/order` | 家人提交点单。body：`{ k: 厨房编号, o: 点单 }` |
| `GET` | `/api/orders?k=` | 下厨端取回点单 |

### 为什么是 `_worker.js` 而不是 `functions/`

Cloudflare Pages 用控制台「上传静态文件」直接发布时，**不能编译 `functions/` 目录**；
而 `_worker.js` 这种"高级模式"入口，用 Wrangler 和用控制台拖拽上传**都支持**。
选它，是为了让这个站在"连 Git 自动构建"和"手动拖个文件夹上去"两种发布方式下
都能跑，不用为了后端换一种部署方式。

### 安全边界

- **只认同源请求**，不返回任何 CORS 头 —— 别的网站没法顶着访问者的身份往这里塞点单，
  这是浏览器替我们把的门。
- 每条点单是一个独立的键（`o:<厨房编号>:<定长时刻>:<id>`），**各家的厨房编号不同，
  互相看不见对方的点单**。
- 所有字段在服务端统一截断（菜名 40 字、留言 200 字、星级夹到 0–5、
  没见过的 `kind` 清成空），所以别人直接 POST 乱七八糟的东西进来，
  也进不了库、上不了你的屏幕。
- 每条点单 7 天后自动过期，不会把免费额度堆满。

## 几处刻意的设计

这些都是踩过坑之后改成的样子，改之前建议先看一眼原因。

**两条通道，而且第二条坏了必须没人知道**
菜单和点单能纯靠链接传，是为了让"服务器不认这个域名"这类故障**不可能导致功能残废**。
在线通道是锦上添花，所以它出的任何问题都不许冒到界面上来 ——
`net.js` 里所有函数失败时只返回 `false` / `null`，绝不抛错。

**回传失败时界面绝不谎称"已经发过去了"**
点菜的人看不到对面，只能信界面上写的。说错了，他就干等着、不再发出去了。
所以 `sent.viaServer` 是提交那一刻的真实结果，并且存进本机 —— 刷新页面也不会变成"已发送"。

**"手动"的东西只许在没后端时出现，有后端时一个都不留**
有过一段过渡期：有后端时把粘贴框收进一个折叠里当"备用"。后来去掉了 ——
已经自动收到的东西旁边再摆一个手动入口，只会让人怀疑前一条路是不是没生效。
现在两种形态是**互斥**的：有后端就是纯自动（页面上连说明文字都不写），
没后端才出现粘贴框，而且它就是主路。
验收脚本两头都盯着：有后端时不许出现 `#order-paste`，没后端时不许出现 `.paste-fallback`。

**清空点单要真的清得掉**
后端只有"写"和"读"、没有删除接口。本地把列表清空之后，下一轮轮询（8 秒）
会把服务端那几条原样拉回来 —— 按钮看上去就是坏的。所以清空时会把那些 id
记进本机的一份 `kf_orders_drop_v1`，轮询时跳过。
验收脚本里真等过一整轮（9 秒）来验这一条，而不是只看一眼列表。

**载荷里的大小写是有意义的，任何地方都不许 `toUpperCase`**
用户粘进来的可能是整条链接、一整段带话的消息、甚至从聊天记录里连"【吃什么】…"
一起复制的，所以要能"从一段乱七八糟的话里把载荷抠出来"。
但转一次大小写就把整份菜单毁了 —— 只有旧的 6 位码才规整成大写。

**二维码一律画成白底黑块，不跟主题走**
深色主题下用主题色画会变成黑底浅块，一样扫不出来。

**版本自检会自己刷新**
静态资源是按网址缓存的，同名文件改了内容不会自动更新。所以每次加载都会悄悄
问一次 `version.txt`，对不上就带新版本号重进 —— 用户不用手动强刷，
点菜的人也不用。这个坑在"你改了、对方看到的还是旧的"里特别难查。

**在浏览器里跑了一遍真实二维码的验收**
`_验收_全流程.js` 和 `_验收_后端.js`（在开发目录里，不随仓库发布）用 jsdom 把整条链路
跑一遍：生成二维码 → **把画布像素用 jsQR 解回原载荷**、断言和原来一字不差；
再把 `window.fetch` 接到真的 `_worker.js` 上，验证"家人提交 → 下厨端自动收到"。
"二维码生成成功"这种话，不解回来就不算验证过。

**「换换口味」抽到的方向是钉住的**
提示词里会写「这次往『一锅出』这个方向想」。这个方向抽出后要记下来，
粘回来时沿用**同一个** —— 因为抽取逻辑天生要避开上一轮那个方向，
两端各抽一次的话，第二次抽到的必然是另一个，界面显示的「这一轮走的是 X」
就和用户手上那段提示词里写的对不上了。
同理，要是用户没走「复制提示词」这一步、直接把别处的回复粘进来，
手上根本没有我们的提示词，这时界面就退回「这一轮的花样」，
不替他编一个没收到过的方向。

## 数据与隐私

- 不收集任何用户数据，没有埋点，没有统计脚本。
- 走离线通道时，**除了那一次 `version.txt` 自检，页面不向任何地址发请求**。
  验收脚本对此有断言。
- 走在线通道时，只有三种请求：一次 `/api/ping`（结果整个会话缓存）、
  提交时一次 `/api/order`、页面开着时每 8 秒一次 `/api/orders`。全是同源相对路径。
- 下厨的人的菜单、点单都存在**自己这台设备**的 `localStorage` 里。
  在线通道上只躺着"传过去的那条点单"，7 天自动过期。
- 清浏览器缓存会丢掉本机的菜单和收到的点单历史，而且**没有账号可以找回**。
  这是"不用登录"的代价。

## 已知限制

- **清缓存丢数据。** 没有账号体系，草稿只在本机。
- **自动收单只对"用新链接分享出去的人"生效。** 家人手上要是旧链接
  （载荷里没有厨房编号），那边不会自动回传，界面会退成"复制，发给下厨的人"。
  他发过来的是一条**点单链接**，你在微信里点一下就能收下 ——
  粘贴框已经去掉了，靠链接一样到得了，只是多一步。
- **在线通道每 8 秒轮询一次**，页面切到后台就停。这是刻意的：省流量、省电，
  而且在免费额度下也更从容。
- **菜的质量取决于你自己那个 AI。** 站里不调任何模型：提示词由 `assets/ai.js`
  拼好给你复制走，菜是你手机上的 AI 出的。菜谱链接来自公开搜索，不保证每条都能打开。
- **安卓版里「看教程」会在系统浏览器里打开**，不在 App 内。
  壳里没有地址栏、没有返回键，开进去就出不来，所以统一交给浏览器。
- **安卓版的自动收单要联网。** 断网时 App 照常能开菜单、看食材、配额，
  只是点单发不出去 —— 那时界面会安静地退回「生成链接 / 二维码」那条离线通道，
  和网页版一致。
- **安卓版不处理分享链接的深链。** 家人收到 `…/#/o/…` 这样的链接，
  点开会进浏览器而不是 App。那条路本身是通的（浏览器里就是同源），所以没加 Intent 过滤。

## 已经砍掉的东西

为了让它在国内网络下真正能发布、并且**不依赖任何"只认自己域名"的服务**，
下面这些已经删干净了（从老版本升级过来的话，不用再找它们）：

- **整条云后端**（`assets/cloud.js` / `assets/config.js` / `assets/vendor/wbcloud.js`）。
  那套服务按来源域名做精确校验、白名单在控制台里改不了，网站一放到别的域名上
  就整片 403 —— 点菜端会报一串错。现在换成"离线通道 + 自带小后端"。
- **6 位菜单码**。它依赖服务器分配，服务器没了它就没了。
  现在菜单直接装在链接和二维码里。老的 6 位码打开时会明确告诉你"现在不用了，让对方重发"。
- **站内模型整条链路** —— `ai.js` 里的 `generate` / `generateSteps`、模型白名单、
  档位表、回退逻辑。现在**整个仓库没有任何一处会去调大模型**。
- **菜品卡上的「让 AI 写做法」** —— 没有站内模型可调了，做法改在「编辑」里手写。
- **整个 `android/` 目录**（下载页 + 1.0 APK + 二维码）。国内安卓手机从 2024 年起
  对未备案的安装包做拦截，自己签的包必然过不了。而浏览器"添加到主屏幕"不经过
  这套校验 —— 这个 App 本来就是一层的浏览器壳，功能全在网页上。

### `backend/` 现在是废弃的

那个目录里是早期云后端的 `schema.sql` / `functions.sql`，写的是两张表加
6 个 `SECURITY DEFINER` 函数。**它对应的前端代码已经不存在了**，
留着只是存档：如果你真想用 Postgres 重建一个中心化后端，这些 SQL 是标准 plpgsql，
在 Supabase 上能直接跑。当前版本不会用到它。

### `assets/ai.js` 现在是什么

它**不联网**了，只干四件事：拼提示词（`ownPrompt`）、解析粘回来的文本
（`ingestExternal`）、判定"家里有没有"（`normalizeDish`）、生成菜谱搜索链接
（`tutorials` / `safeUrl`）。

⚠️ 但它**仍然不是自包含的**：`guest.js` 用到其中一个函数 `AI.safeUrl`
（点"打开菜谱来源"那一刻）。想把它拆走的话，先把这些纯工具挪到别的文件
（比如 `assets/ui.js` 或新建一个 `assets/dish.js`），改好两端的引用再删 ——
**直接删 `ai.js` 会让点菜端在"打开菜谱来源"时崩**，而不是打开页面就崩，很难第一时间发现。
